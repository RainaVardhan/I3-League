# i3League — Stage 4: ITERATE — Activities

## By Topic

| Topic | Activity | Worksheet | Output | Artifact Contribution |
|---|---|---|---|---|
| MVP Thinking | Smallest Testable Version — reduce the chosen concept to the smallest version that can test the critical assumption | MVP Planner | MVP definition + what it is meant to learn | Test Plan |
| Prototype Fidelity | Choose the Right Fidelity — decide whether the test needs a sketch, mockup, physical model, simulation, or working version | Prototype Fidelity Selector | Chosen fidelity + justification | Test Plan |
| Experiment Design Basics | One-Thing Test — define the one important thing being tested and keep other conditions as consistent as practical | Test Plan | Simple experiment structure | Test Plan |
| Test Questions & Success Criteria | Define Success Before Testing — write the test question and measurable success criteria before running the test | Test Question & Success Criteria Builder | Test question + success threshold | Test Plan |
| Usability Basics | Silent Use Test — give the prototype to someone unfamiliar with it and observe without explaining unless safety requires it | Usability Observation Sheet | Usability observations | Feedback Log |
| Observation vs. Opinion | Watch vs. Ask — record what testers actually did separately from what they said afterward | Observation vs. Opinion Log | Behavior evidence + reported feedback | Feedback Log |
| Learning From Failure / Failure Logging | What Did This Teach Us? — record failed, partial, surprising, or inconclusive outcomes and what they revealed | Failure / Learning Log | Meaningful learning entries | Iteration Log |
| Feedback → Revision | Evidence-to-Change — connect each meaningful finding to a specific design change, or explain why no change was made | Feedback Log + Iteration Log | Feedback-to-revision links | Iteration Log |
| Versioning / Iteration History | V1 → V2 → V3 — preserve each meaningful prototype version and document what changed and why | Version History | Version sequence + change rationale | Iteration Log |
| Team Execution & Task Tracking | Build Sprint — assign current tasks by owner, deadline, status, and blocker | Team Task Tracker | Active execution board | Project record |
| Formal Experiment Controls *(HS CORE)* | Controlled Test Design — identify variables, controlled conditions, and comparison/control group when appropriate | Formal Experiment Design | More rigorous experiment plan | Test Plan |
| Git & Technical Documentation *(HS CORE, when relevant)* | Document the Build — create version-control checkpoints and explain how the technical project works | Technical Documentation / Git Checklist | Repository/version evidence + README | Iteration Log / technical evidence |

## Supporting Activities

| Activity | Worksheet | Output | Why it's needed |
|---|---|---|---|
| Pilot/Test Participant Plan | Test Plan | Who will test, how many, where, when, permissions needed | Makes testing real and safe rather than informal |
| Retest After Revision | Iteration Log + Test Plan | Evidence from at least one revised version | Proves iteration actually happened — not just Test → change → stop, but Test → Learn → Revise → Retest |

## Stage 4 Output Rollup

MVP Planner + Prototype Fidelity + Test Question + Success Criteria + Test Evidence + Feedback + Learning Log + Revision History + Retest Evidence combine into the required artifact:

**Tested Prototype + Test Plan + Iteration Log**

For software/technical projects, optionally add: **Repository + Technical README**

## Advancement Check for Stage 4 (strengthened)

Student can show:
- a real test of the critical assumption
- a clearly defined MVP/testable version
- test question and success criteria written before testing
- observed behavior and reported feedback
- meaningful learning from the test
- at least one evidence-based revision
- **evidence that the revised version was tested again (retest)**

This strengthens the frozen closing bar by explicitly requiring the retest — a student proving "we tested it, found a problem, changed it" is not enough; they must also show whether the change actually helped.

## Required Loop

**Critical Assumption → MVP → Test → Observe → Learn → Revise → Retest → Document → Advance**
